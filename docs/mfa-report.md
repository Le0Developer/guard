# MFA port

Implemented TOTP enrollment/login with AES-256-GCM user-bound secrets, SHA-1 six-digit 30-second codes, ±1 step drift and persisted replay prevention. Recovery codes contain 128 random bits, normalize like Rust, are hashed with user binding and consumed transactionally. Security key enrollment/login uses go-webauthn v0.18.2 with persisted expiring single-use challenges, session/login binding, account revisions, invalid attempt tracking and sign-counter clone rejection.

Management supports /security, /account/security and administrator target routes, method renaming/removal, backup code replacement and explicit reset. All management requires a current session authenticated within five minutes. Changes invalidate ceremonies and revoke other owner sessions; administrator changes and explicit reset revoke all target sessions. Final method removal requires reset. Global middleware provides CSRF validation. Login completion uses the shared finishLogin helper after factor consumption, which rechecks the login session and account revision.

Tests cover RFC TOTP output, encryption identity binding, recovery normalization, allowed WebAuthn origins, concurrent recovery consumption, TOTP replay/browser binding, ceremony expiry/revision, recent management sessions and cross-user denial, session revocation and persisted WebAuthn registration challenges/invalid attempts. Initial test runs demonstrated missing implementation. Final MFA suite passes against PostgreSQL: `go test ./internal/app -run TestMFA -count=1` (0.834s) and `go test -race ./internal/app -run TestMFA -count=1` (5.400s), using the supplied test database and isolated schemas. Parent reports full integration passing (2.186s). Review tightened account/session locking to serialize revocation and avoid cross-administrator lock-order deadlocks; WebAuthn finish attempts consume their challenge even on rejection.

TOTP setup displays a manual secret and an otpauth link; it does not render a QR code because no QR dependency is allowed. Physical authenticator verification remains a manual browser check. The final session write follows the committed factor transaction: if session issuance fails, the factor remains consumed and authentication fails closed.
